# Permanent deletion and sync

The v1.3 client stores permanent deletion IDs and its receipt checkpoint in the same account database as local content. A receipt page removes content and stale content operations, retains review history, and advances the checkpoint in one SQLite transaction. Clearing or recreating that database resets the checkpoint. Permanent IDs also prevent an old fetch response or stale undo handle from recreating removed content.

`GET /sync/purged?cursor=N` returns at most 500 receipts, `next_cursor` when another page exists, and `checkpoint_cursor` even for the terminal page. Receipt IDs and cursors are decimal strings. Writers and the receipt reader share the account transaction lock so a checkpoint cannot pass an earlier uncommitted receipt for the same account. Upload, creation, and purge also acquire consistently ordered locks from 64 shared stripes derived from content IDs before checking or creating either a live row or a receipt. This bounds PostgreSQL advisory-lock memory independently of library size. Cleanup scans deletion candidates and verifies the current content owner when deleting rows.

New clients request `include_purged=false` on the manifest and in fetch payloads. This omits permanent receipts from normal revision/card enumeration; requested purged deck IDs can still be represented by a content-free tombstone if a purge happens between manifest and fetch. The incremental receipt endpoint remains authoritative. Omitting the option preserves the legacy manifest/fetch/download contract for older clients. An older server may ignore the option: the client's local permanent-ID ledger still suppresses receipt rows. Servers without a terminal checkpoint cursor replay at most their final receipt page; servers without the receipt endpoint retain their older soft-deletion behavior.

Deck titles accept up to 255 Unicode characters, matching PostgreSQL `VARCHAR(255)`. Description, front, and back retain their historical `TEXT` behavior, bounded by the 4 MiB HTTP request limit. Normal offline edits validate title length and individual payload size before committing. Sync batches target 1 MiB and 200 operations. Invalid JSON and individually oversized queued operations remain recoverable locally. Atomic server validation/size failures are split to isolate rejected operations, allowing valid operations to continue. A sync with rejected pending changes reports a warning and does not advance the last-successful-sync time.

Account metadata deletion invalidates active sync sessions and serializes manifest writes with removal of both final and temporary files. A late response from the deleted session cannot recreate its manifest.
